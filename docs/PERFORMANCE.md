# Performance: targets, budgets, benchmarks

Performance is the reason Fotox exists. A feature that misses its target is
not done.

## 1. Reference machine

| | |
| --- | --- |
| OS | Windows 10/11, 64-bit |
| RAM | 16 GB |
| GPU | NVIDIA RTX 3060, 12 GB VRAM (DX12 via wgpu) |
| Scratch | NVMe SSD, **< 100 GB free** |

All targets below are for this machine, **release build**.

## 2. Budgets

### RAM (16 GB)

| Consumer | Budget |
| --- | --- |
| Windows + other apps | ~3 GB |
| CEF / UI processes | ~0.6 GB |
| Tile store, hot (`hot_budget`) | 5 GiB |
| Tile store, warm LZ4 (`warm_budget`) | 3 GiB |
| Working buffers (import bands, filter aprons, staging) | ≤ 1.5 GiB |
| **Fotox peak** | **≈ 10 GB, whatever the document size** |

### VRAM (12 GB)

| Consumer | Budget |
| --- | --- |
| Tile atlas (source tiles + composite cache) | 6 GiB (~12 000 tiles of 256² Rgba16Float) |
| Viewport / swapchain / UI textures | < 0.5 GiB |
| Filters' temporary buffers | ≤ 1 GiB |
| Headroom (driver, other apps) | rest |

### Scratch disk

* Hard cap `scratch_limit` = 60 GiB (preference). Warn in the status bar at 80 %.
* Only authoritative tiles go there. Derived tiles are recomputed instead.
* Tiles of an opened `.fxd` are read from that file, never copied (M3).

### The physics, honestly

A fully painted 30 000² layer is 3.6 GB at 8-bit and **7.2 GB at 16-bit**.
Photographic 16-bit data compresses badly without loss (LZ4 ≈ 1.1–1.4×; the
low bits are noise). So with 60 GiB of scratch, **about 8–10 fully painted
16-bit 30k layers** is the real ceiling of the reference machine — for
Photoshop too. What makes "hundreds of layers" possible is that real
compositing documents are mostly **sparse** (cut-outs, retouch layers, masks,
adjustment layers): empty tiles cost nothing and adjustment layers cost no
pixels. The benchmark documents reflect that.

## 3. Benchmark documents

Generated by `fotox-cli gen` (M1-T10) — deterministic (fixed seed), with
photo-like content (smooth gradients + multi-octave noise + grain), so
compression ratios are realistic, not flattering.

| Id | Content |
| --- | --- |
| **B1** | 30 000 × 30 000, 16-bit RGB TIFF, one layer (5.4 GB file) |
| **B2** | 30 000 × 30 000, 8-bit RGB TIFF, one layer |
| **B3** | B1 as background + 199 sparse pixel layers (each 2–10 % of the area, random blend modes and opacities) + 20 adjustment layers (M2+, `.fxd`) |
| **B4** | 12 000 × 8 000, 16-bit, 50 layers — "normal big" retouch file |

Files go to `bench/data/` (git-ignored). Results are appended to
`bench/results.csv`: `date,commit,scenario,document,metric,value,unit,notes`.

## 4. Scenarios and targets

| Id | Scenario | Target | Milestone |
| --- | --- | --- | --- |
| S1 | Open B1 (TIFF import) | first full view (low-res) < 3 s; import throughput ≥ 80 % of raw disk read speed | M1 |
| S2 | Pan/zoom B1, fit ↔ 3200 %, continuous | ≥ 60 fps, no frame > 33 ms; full detail < 250 ms after stopping | M1 |
| S3 | Open B3 (`.fxd`) | first frame < 1 s | M3 |
| S4 | B3: toggle visibility / change blend of a mid-stack layer | viewport updated < 100 ms (fit) / < 50 ms (100 %) | M2 |
| S5 | B3: drag opacity slider of a mid-stack layer | ≥ 30 fps live | M2 |
| S6 | B3: add Curves adjustment on top, drag a point | ≥ 30 fps live | M2 |
| S7 | B3: save after changing one layer | < 2 s | M3 |
| S8 | Any document | RSS ≤ 10 GB; scratch ≤ limit | always |
| S9 | 500 px brush stroke on a 16-bit layer of B1 at 100 % | input → pixels ≤ 16 ms | M5 |

Engine-only scenarios (S1 throughput, tile trim/compress speed, mip
generation, composite-tile throughput) run in `fotox-cli bench`. GUI scenarios
use the in-app FPS/frame-time overlay (M1-T12) plus a screen recording.

### Comparing with Photoshop (done by Rob)

Same machine, same files, Photoshop's default performance settings (note RAM
% and cache levels used). For each scenario: 3 runs, median, stopwatch or
screen recording at 60 fps. Record rows in `bench/results.csv` with
`document=photoshop:<file>`.

## 5. Code rules that follow from this

* No buffer proportional to the document size. Ever. (Bands and tiles only.)
* No per-pixel heap allocation, no per-pixel `match` on format in hot loops.
* Never hold a lock while doing I/O, compression, or GPU waits.
* The render thread never blocks on disk or on the engine.
* Release mode for any measurement (`cargo run --release`, or the
  `profiling` profile for symbols).
* Every performance-sensitive task states its target and shows the measured
  number in its report.
