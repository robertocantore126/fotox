# M0 — Shell

Goal: `fotox.exe` runs the Fotox UI inside the vendored Graphite shell, with
a native wgpu viewport under it, input routed correctly, and the UI ↔ engine
protocol alive. No document yet: the viewport shows a procedural test pattern
of a virtual 30 000 × 30 000 document.

Read first: `AGENTS.md`, `docs/ARCHITECTURE.md` §2, `docs/GRAPHITE.md`,
`docs/PROTOCOL.md`.

---

## M0-T01 — Toolchain and first build on Windows

**Goal** Prove the workspace and the vendored shell build on the reference machine.

**Steps**
1. Install: Rust via rustup (stable, `x86_64-pc-windows-msvc`), Visual Studio
   2022 Build Tools with the "Desktop development with C++" workload, CMake,
   Ninja (both on `PATH`), Git.
2. `cargo test` at the repo root (engine crates only, no CEF).
3. `cargo build -p fx-app`. The first build downloads CEF (~300 MB) into
   `third_party/cef/` (configured in `.cargo/config.toml`).

**Acceptance**
* Both commands succeed with no warnings in our crates.
* `third_party/cef/` is populated and git-ignored.

**Report** Tool versions (`rustc -V`, `cmake --version`, `ninja --version`),
build times for both commands, any error and its fix.

## M0-T02 — `xtask`: bundle and run

**Goal** One command builds `fotox.exe`, places it next to the CEF runtime,
and launches it. (CEF needs `libcef.dll` and its resources beside the exe.)

**Port from** `reference/graphite-desktop/bundle/src/{win.rs,common.rs}`.

**Files** `tools/xtask/` (new crate, add to workspace members but not to
`default-members`), `.cargo/config.toml` (alias).

**Steps**
1. Create `tools/xtask` binary crate. Commands:
   * `cargo xtask bundle [--release]` → `target/<profile>/Fotox/` containing
     the CEF runtime from `$CEF_PATH/<version>/<os_arch>/` (same layout
     `cef-dll-sys` created) plus `fotox.exe`.
   * `cargo xtask run [--release] [-- args]` → bundle, then launch.
2. Apply Graphite's `remove_unnecessary_cef_files` list (keep only `en-US.pak`
   in `locales/`).
3. Add `[alias] xtask = "run -p xtask --"` to `.cargo/config.toml`.
4. Re-copy only files whose size/mtime changed (keeps iterations fast).

**Acceptance** `cargo xtask run` starts the current placeholder `fotox.exe`
from the bundle folder (it prints its M0 message and exits).

## M0-T03 — Shell: window + CEF + Fotox UI

**Goal** The app window shows the complete Fotox UI, rendered by CEF, fully
interactive (menus, flyouts, panels, dialogs, resizing the dock).

**Port from** `reference/graphite-desktop/src/`: `lib.rs`, `app.rs`,
`window.rs`, `window/win.rs`, `window/win/native_handle.rs`,
`gpu_context.rs`, `event.rs`, `consts.rs`, `dirs.rs`, `cli.rs`,
`preferences.rs`, and `render/state.rs` + `composite_shader.wgsl`. See the
table in `docs/GRAPHITE.md` §2 for what to keep and drop.

**Files** `crates/fx-app/src/*.rs`, `crates/fx-app/src/composite.wgsl`,
`crates/fx-app/Cargo.toml` (add approved deps as needed; if you need a crate
not in `[workspace.dependencies]` — e.g. `fd-lock`, `ctrlc`, `dirs`, `ron`,
`thiserror` — add it there with the version Graphite uses and a line in
`DECISIONS.md`).

**Steps**
1. `main`: call `UiContext::setup()` **before anything else**; return the
   helper exit code for CEF subprocesses. Then logging, single-instance lock
   (`%APPDATA%/Fotox/instance.lock`), wgpu device (DX12 preferred, adapter
   override `FOTOX_WGPU_ADAPTER`; request `required_limits` with at least
   the adapter's `max_texture_array_layers` — the tile atlas needs 2048;
   create it through `wgpu_sync::Instance`/`Adapter` so the queue is a
   `wgpu_sync::Queue`, see `crates/fx-render/src/gpu/tests.rs::gpu()`), winit event loop, `UiContext::start`,
   `ui_context.instance(&device, &queue)`, `ui-events` bridge thread.
2. `App` (`ApplicationHandler`): create the window (title "Fotox",
   1600 × 1000 default, min 1024 × 700), configure the surface, forward
   resize/scale changes (`UiCommand::Resized`, `ScaleChanged`, `Refresh`),
   bind each `UiEvent::Frame(texture)` and request a redraw, apply
   `UiEvent::Cursor`, exit cleanly on close (call `ui.shutdown()`).
3. Render: port Graphite's composite pass. Until T04 there is no viewport
   texture: bind a 1 × 1 transparent texture; background colour `#282828`.
4. Input: forward **all** winit input to the UI for now
   (`UiCommand::Input`), using Graphite's `input.rs` event conversion.
5. `--disable-ui-acceleration` flag and Graphite's automatic restart with
   acceleration disabled on `UiAccelerationFailure`.
6. The UI loads from `./ui` via `GRAPHITE_RESOURCES` (dev). No UI code
   changes in this task.

**Acceptance**
* `cargo xtask run`: window opens in < 3 s, the Fotox UI looks exactly as in
  a browser (`python tools/serve.py` inside `ui/` for comparison), all menus
  and dialogs work with mouse and keyboard, window resize and moving between
  monitors with different scaling keep the UI sharp.
* Closing the window leaves no `fotox.exe` process running.
* `GRAPHITE_BROWSER_DEBUG_PORT=9222` lets you inspect the UI in Chrome
  DevTools.

**Out of scope** Viewport content, protocol, engine.

## M0-T04 — Viewport texture and the transparent hole

**Goal** The UI's workspace area is transparent and the shell draws a native
texture there.

**Files** `ui/index.html`, `ui/css/app.css`, `ui/js/canvas.js`,
`ui/js/native/bridge.js` (new), `crates/fx-app/src/{app.rs,render.rs}`.

**Steps**
1. UI, native mode only (`bridge.isNative` = `typeof window.sendNativeMessage === "function"`):
   * add `body.native`; make `html`, `body`, `#app` and every ancestor of
     the workspace transparent; every chrome element keeps its own opaque
     background (check menu bar, options bar, tool column, dock, status bar,
     doc tabs, rulers).
   * in `canvas.js`, in native mode, do not create the demo `<canvas>`;
     create `<div id="viewport">` filling `.workspace-main` instead.
2. Implement the receive side of `bridge.js`: install
   `window.receiveNativeMessage`, then call
   `window.initializeNativeCommunication()`; expose
   `send(obj)` / `sendBinary(header, bytes)` / `on(type, fn)` using the
   framing in `PROTOCOL.md` §2 (put framing + message type constants in
   `ui/js/native/protocol.js`).
3. Send `viewport_bounds` (rect × `devicePixelRatio`) from a
   `ResizeObserver` on `#viewport` and on `window.resize`.
4. Shell: decode UI messages with `fx_protocol::decode`; handle
   `viewport_bounds` like Graphite's `UpdateViewportPhysicalBounds`
   (viewport offset/scale uniforms). For now fill the viewport texture with a
   flat `#3a3a3a` + a 1 px red border, recreated on resize.

**Acceptance** The grey area with the red border sits exactly inside the
workspace (no gap, no overlap with rulers/tabs) at 100 %, 125 %, 150 % Windows
scaling, after dock resizing and in all three screen modes (`F`).

## M0-T05 — Protocol bridge and mock engine

**Goal** UI and native talk in both directions; the UI still works in a
plain browser.

**Files** `ui/js/native/{bridge.js,protocol.js,mock-engine.js}`,
`ui/js/actions.js`, `ui/js/main.js`, `crates/fx-app/src/bridge.rs`.

**Steps**
1. `protocol.js`: constants for every message type in `fx-protocol`, plus
   `encodeJson`, `encodeBinary`, `decode` (mirror of the Rust functions).
2. `bridge.js` in browser mode: route `send` to `mock-engine.js`, which
   answers `hello` with a `toast` and `action` with `toast` "not implemented
   (mock engine)". The UI must keep working exactly as before in a browser.
3. On load, send `hello {ui_version}`.
4. `actions.js`: keep all current local behaviour; additionally send every
   action id as `{type:"action", id}`. Remove the local "mock" toasts for
   actions the engine will own later only when the engine handles them (not
   in this task).
5. Direct input: whenever a popup/menu/drop-down/flyout/dialog opens or
   closes (hook into `popup.js` and the dialog engine), send
   `direct_input {enabled}` (`false` if anything is open).
6. Shell `bridge.rs`: until the engine exists (T06), answer `hello` with
   `toast {text:"Engine connected"}` and log every other message at `debug`.

**Acceptance** In the app, the toast "Engine connected" appears at startup;
menu actions show in the log; with a menu open over the canvas the
`direct_input false` message is logged, and `true` when it closes. In a
browser, the UI still works and shows the mock toasts.

## M0-T06 — Engine thread, input routing, test-pattern viewport

**Goal** A real engine thread owns a view of a *virtual* 30 000² document;
pan/zoom works with mouse, wheel and pen; the UI rulers and zoom readout follow.

**Files** `crates/fx-engine/src/*`, `crates/fx-render/src/{test_pattern.rs,test_pattern.wgsl}`,
`crates/fx-app/src/{input.rs,bridge.rs,app.rs}`, `ui/js/canvas.js`, `ui/js/native/*`.

**Steps**
1. `fx-engine`: `EngineHandle::spawn(device, queue: wgpu_sync::Queue)` starts
   the engine thread (crossbeam channel of `EngineInput`) and a render thread.
   Outputs go back through a callback the shell provides (it wraps winit's
   `EventLoopProxy`). Add `EngineOutput::ViewportFrame(wgpu::Texture)`.
   **All queue submissions from the render thread go through the
   `wgpu_sync::Queue`** (surface reconfiguration on the main thread would
   otherwise race and crash the driver — see the crate docs).
2. View state: `fx_render::ViewTransform` for a virtual 30 000 × 30 000
   document, initialised with `fit`. Handle:
   * wheel → vertical pan; Shift+wheel → horizontal pan; Ctrl/Alt+wheel →
     `zoom_at` cursor (factor 1.1 per notch, smooth for pixel deltas);
   * drag with middle button, or Space+left drag, or tool `hand` → `pan_screen`;
   * actions `zoom:in`, `zoom:out` (`step_zoom`), `zoom:fit`, `zoom:100`
     (centre kept);
   * `set_zoom`.
   After each change: send `view` to the UI (throttle to 60 Hz) and render.
3. Render thread: draw `test_pattern.wgsl` into a double-buffered viewport
   texture (`Rgba8Unorm`, **not** sRGB — the composite pass treats it as
   sRGB-encoded values, and `fx-render`'s `ViewportRenderer` requires a
   non-sRGB target), viewport size: 256-px checker in document space
   (so it scales/moves with zoom/pan), a thicker line every 4096 px, document
   bounds in cyan, outside the document `#282828`. Send
   `ViewportFrame(texture)` when done; the shell binds it and redraws. Only
   render when something changed.
4. Shell input routing (port Graphite's `input.rs` routing logic): pointer
   inside viewport rect and `direct_input` enabled → `EngineInput::Pointer`
   (coordinates relative to viewport, pressure/tilt from winit tablet data,
   `time_us`), wheel → `EngineInput::Wheel`; else → UI. A drag that started
   in the viewport keeps going to the engine until release. Space is tracked
   as a modifier.
5. UI: in native mode, rulers and the status-bar zoom field are driven by
   `view` messages (document ↔ screen mapping from zoom, centre and viewport
   size), not by DOM scrolling. The status bar zoom field sends `set_zoom`.

**Acceptance**
* Pan/zoom over the whole range 1 %–3200 % at ≥ 60 fps (frame time overlay
  not needed yet: use PresentMon or the NVIDIA overlay) in a 1600 × 1000
  window.
* Ctrl+wheel keeps the point under the cursor fixed.
* Rulers match the pattern: the 4096-px lines sit on the right ruler ticks
  at any zoom.
* With a menu open over the canvas, clicks go to the menu, not the viewport.
* A Wacom/Windows Ink pen pans with Space held (pressure logged at `trace`).
