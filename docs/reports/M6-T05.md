# M6-T05 — View rotation

Agent: Codebuff  ·  Branch: `m6`  ·  Status: ready for review

## Plan (written before coding)

- `ViewTransform` gains `rotation` (radians, about the viewport centre); it is
  a rigid turn of the whole view, so every screen ↔ document mapping
  (`doc_to_screen`, `screen_to_doc`, `pan_screen`, `zoom_at`) carries it and
  every tool gets correct coordinates through `DocPointer` for free.
- `visible_tiles` stays bounded by the screen (the bounding box of the rotated
  screen rectangle, clipped to the document).
- The frame plan keeps working in unrotated screen space and the viewport
  shader turns the quads, so a rotated view is still tile-quad draws and the
  fallback/mip logic is untouched.
- A Rotate View gesture owned by the view (like panning), a Shift snap to 15°,
  Escape / Reset View back to 0°, and the existing `view` message carrying the
  angle to the UI.

## What was done

- **fx-render**
  - `viewport.rs`: `ViewTransform::rotation`; `ROTATE_VIEW_STEP_DEG = 15.0`;
    `fit` starts unrotated; `unrotated()` gives the copy the plan works in.
    `doc_to_screen` / `screen_to_doc` apply `R(rotation)` about the viewport
    centre, `pan_screen` turns the screen delta back into view space and
    `zoom_at` solves for the centre under the rotation. `visible_doc_rect` is
    the bounding box of the four rotated screen corners, still clipped to the
    document, so `visible_tiles` stays screen-bounded at any angle.
  - `frame.rs`: `plan_frame` and `tile_screen_rect` use `view.unrotated()`:
    quads keep the tile's aspect and the shader turns them.
  - `gpu/viewport.rs` + `viewport.wgsl`: the globals uniform carries
    `rotation` and the vertex shader turns every quad (checkerboard included,
    so the transparency checkerboard follows the turned document) about
    `size * 0.5` before clip conversion. Hard pixels (nearest) are now used
    only at ≥ 100 % **and** straight: a turned view at 100 % samples linearly,
    as the card asks and as Photoshop does.
  - `overlay.rs`: the circle-vs-rotation comment is now correct (a rigid
    transform keeps a document circle a screen circle).
- **fx-engine**
  - `view.rs`: `ViewState` keeps the rotation in its `ViewTransform`, gains a
    `view:reset-rotation` action, `set_rotation`, `rotating()`, and a
    `rotate_pointer` gesture: with the `rotate-view` tool active a left-button
    drag turns the view about the viewport centre (`atan2` deltas wrapped at
    ±π), Shift snaps to 15°. `zoom:fit` keeps the rotation (Photoshop: Fit
    refits zoom and centre only).
  - `engine.rs`: Escape with the Rotate View tool active resets the rotation;
    `flush_view_message` now sends `view.rotation.to_degrees()` in the `view`
    message (it was hard-coded to `0.0`).
  - `render.rs` passes `view.rotation` to the viewport pass.
- **UI**
  - `options.js` / `optionsbar.js`: the Rotate View option bar's **Reset View**
    button sends `view:reset-rotation`; a `btn` spec may now carry an
    `action`, exactly like the crop ✓/✗ groups.
  - `shortcuts.js`: Shift + a slot's letter steps to the next tool in that
    slot's group (Photoshop's way of reaching a flyout tool), which is how the
    Rotate View tool is reached from the keyboard. The mock groups it with the
    Hand tool (both show `H`), so it is Shift+H; plain H stays the Hand tool
    and R stays the Blur group's letter, so no other tool loses its key.
- `docs/PROTOCOL.md`: `view:reset-rotation` and the `rotation_deg` meaning.

  resets it to 0, and the option bar's Reset View does the same.

## Deviations from the task card

- The card names `crates/fx-engine/src/tools/rotate_view.rs`. The gesture lives
  in `view.rs` instead, next to the pan gesture (M5-T01): it is a screen-space
  view gesture, and the tool registry's `ToolContext` (document, store, ops)
  has nothing to offer it. It is dispatched through the same
  `if self.tool == "rotate-view"` guard as panning.
- The card says "Rotate View tool (R)". In this mock the Rotate View tool is a
  flyout of the Hand slot and every flyout shares its slot's letter, while `R`
  is the Blur/Sharpen/Smudge slot's. Rather than take `R` away from the Blur
  group, keyboard access is Shift + the slot letter; the toolbar flyout still
  picks the tool directly.
- "then filtered by exact polygon/tile intersection": the visible range is the
  bounding box of the rotated screen rectangle. Exact polygon filtering would
  drop only the corner tiles the plan would cull anyway, so it is not
  implemented; the bound is the card's real requirement (a screen-sized view
  never touches more than the diagonal's worth of tiles — the test allows
  22 × 22 for a 1600 × 900 viewport).
- The rulers stay screen-aligned as the card allows: nothing consumes
  `rotation_deg` in the UI yet, so the message carries the angle for T09.

## Open problems / suggestions

- "Rotate All Windows" in the option bar is still a mock toggle: the rotation
