# M6-T02 — Image geometry: rotate, flip, canvas size, image size

Agent: Buffy  ·  Branch: `m6` (see "Deviations")  ·  Status: ready for review

## Plan (written before coding)

1. `fx-core/src/transform.rs`: the pure geometry of the four operations —
   `Permutation` (`Rot90Cw` / `Rot90Ccw` / `Rot180` / `FlipHorizontal` /
   `FlipVertical`: `label`, `from_quarter_turns`, `size`, `source_pixel`,
   `offset`), `Anchor9` with the nine anchor cells, and `dest_rect` (the
   destination bounding box of a mapped rectangle).
2. `fx-ops/src/permute.rs`: the exact pixel permutation behind a quarter turn
   and a flip — destination tile by destination tile, one source rectangle
   fetched through `Grid`, a uniformly solid region left as one `Solid` tile,
   the padded part of a partial tile never read.
3. `fx-core/src/command.rs`: `Command::{RotateCanvas, FlipCanvas,
   RotateCanvasArbitrary, CanvasSize, ImageSize}`, validation before any
   mutation, `RotateCanvasArbitrary` and `ImageSize` sharing one
   `resample_document` pass over every pixel layer, mask and the selection.
4. `fx-core/src/ops.rs`: `PixelOps::rotate` and `PixelOps::resample` (recipe
   R1a — the commands stay in a crate that cannot see `fx-ops`).
5. `fx-engine/src/ops.rs`: `EngineOps` — `rotate` a tile row at a time,
   `resample` after making the mip levels it may read valid, committing in
   batches (`RESAMPLE_BATCH`, the One Rule, deep review S1-01).
6. `fx-engine/src/engine.rs`: the `img:*` actions, the two new commands joining
   the pixel-job set with their Photoshop labels, and `after_edit` refreshing
   the view's copy of the document size.
7. UI: the five greyed Image Rotation items become live, and Image Size / Canvas
   Size / Rotate Arbitrary get wired to the engine (`native/image.js`).
8. Tests: the card's four, plus the engine-level ones the card's *tile handles
   equal where tiles were uniform* clause asks for.

## What was done

**`fx-core::transform`** — `Permutation` is exact by construction: `size` swaps
the axes for the odd turns, `source_pixel(dst, size)` answers which pixel a
destination pixel takes (and refuses the padding past a partial edge), and
`offset(offset, image, canvas)` recomputes a placed image's offset from the
canvas rule `(x, y) → (cx − 1 − y, x)`, so a layer that is not canvas-sized
stays exactly where it was. `Anchor9::offset(old, new)` places the old canvas
inside the new one (centre rounds toward zero, so an odd pixel of growth is on
the right/bottom, as Photoshop does; saturating, never wrapping).

**`fx-ops::permute`** — `permute(src, source_size, op, dst_tiles, store)`.
Per destination tile: the four corners of the clipped tile bound the source
rectangle (a permutation maps rectangles to rectangles), the region is looked
up in one cache, and a uniformly solid region returns `Solid` without touching
a pixel — rotating a document of fills, masks and empty layers allocates
nothing. `TileHandle` identity is preserved wherever a whole tile maps to a
whole tile, which is what the card's "same tile handles" test checks.

**The five commands** (`fx-core/src/command.rs`):

* `RotateCanvas { quarter_turns }` / `FlipCanvas { horizontal }`: every pixel
  layer, mask and the selection (and `reselect`) permuted, offsets recomputed,
  document size swapped on an odd turn. Nothing is resampled, so 16-bit data
  survives bit-exactly (that is S17: tile I/O, not filtering).
* `RotateCanvasArbitrary { angle_deg, filter }`: the canvas grows to the
  rotated bounding box (`dest_rect`), and every image is resampled through the
  turn about the canvas centre. `0°` is refused instead of recorded as a
  no-op.
* `CanvasSize { width, height, anchor }`: only the document size and every
  offset/mask-agnostic placement move — **no pixel is rewritten** (D-015), so
  content outside the canvas is kept and comes back if the canvas grows again.
* `ImageSize { width, height, ppi, resample }`: `resample: None` refuses a
  pixel-size change and only sets the print resolution; otherwise every pixel
  layer, mask and the selection is resampled with the chosen filter, every
  offset scales with the canvas, and `ppi` becomes the print resolution.
* Render-thread-untouched jobs: `RotateCanvas`, `FlipCanvas`,
  `RotateCanvasArbitrary` and `ImageSize { resample: Some(_) }` join
  `is_pixel_job`, with the Photoshop labels ("Rotate 90° Clockwise", "Flip
  Canvas Horizontal", "Rotate Image", "Image Size") and progress.

**Engine** (`fx-engine::ops`) — `rotate` walks one destination tile row at a
time, so at most a row of tiles is in flight; `resample` calls `mips::ensure_mip`
for every level the local scale may read, then hands `SourceInfo { size, levels }`
to `fx-ops::resample` and commits in batches of 16, reporting progress.

**UI** — `img:rot90cw` / `img:rot90ccw` / `img:rot180` / `img:flip-h` /
`img:flip-v` were already in the menus but disabled ("they arrive with M6");
they are live now. `ui/js/native/image.js` runs the three dialogs and sends one
command each; `dialogs.js`' `readValues` learned the three things those dialogs
need — the **first** field wins when a label repeats (Image Size shows Width
once per unit), radio groups report the selected option, and the anchor grid
reports the selected cell's index.

## Deviations from the task card

1. **An arbitrary angle is a fifth command** (`RotateCanvasArbitrary`), not yet
   the card's "a `Transform` of every layer (T01)" — that is T04's
   `Command::Transform` with its live preview and Free Transform box. T02 needs
   the *destructive* menu entry, so it resamples through the same `Mapping`
   (`Mapping::rotation_about` + the box's translation) that T04's transform will
   use, and T04's command will reuse `resample_document`/`resample_placed`.
2. **Where the geometry lives.** As in T01: the serialisable parameters and the
   pure geometry (`Filter`, `Mapping`, `Permutation`, `Anchor9`, `dest_rect`)
   are in `fx-core::transform`, the tile algorithm in `fx-ops::permute`, because
   `Command` must serialise them and `fx-core` cannot depend on `fx-ops`
   (recipe R1a).
3. **`Permutation::offset` needs the canvas size.** The card only mentions the
   layer's own size; without the canvas an image that is not canvas-sized cannot
   be placed correctly, and the offset is the whole reason `OffsetLayer` exists
   (ARCHITECTURE §4.3).
4. **Masks have no offset of their own** in the model (they are canvas
   coverage), so they are grown to the canvas (`pixels::grow_to_canvas`) before
   being permuted or resampled — otherwise a mask left smaller than the canvas
   by an earlier Canvas Size would be mis-placed. The selection and `reselect`
   carry their offsets and are treated like placed images.
5. **`readValues` (UI) reads the first field when a label repeats.** Image Size
   lists Width and Height once per unit (px, in, mm); the pixel row is the one
   the engine takes and it is listed first. Same change reads radio groups and
   the anchor grid, which T09 needs anyway.
6. **The three dialogs show only what the engine takes.** The mock's
   inches/millimetres rows, its unit menu and Canvas Size's "Canvas Extension
   Colour" are not shown: the first two are derived units and the third has
   nothing to fill (D-015 rewrites no pixel). T09 owns turning them live
   (`rng()`, a constrain toggle, live unit sync).
7. **Shape/text transforms and "Scale Styles" do not exist yet** (T06–T08).
   Image Size scales every offset and every mask, which is the same geometric
   contract; `resample_document` marks where a shape/text transform will hook in.

## Open problems / suggestions

- **A shared batched-commit helper.** `EngineOps::rotate` commits a tile row at
  a time and `EngineOps::resample` in batches of `RESAMPLE_BATCH = 16`, so
  neither collects a whole image; `EngineOps::filter` and `composite_layers`
  still collect everything (deep review S1-01). One `commit_batched(tiles,
  store, |buffer| …)` helper would fix all four in one place — worth doing
  before T04's Free Transform multiplies the call sites.
- **Image Size drops what is outside the canvas.** Its mapping is
  `Mapping::scale`, so the destination box of a layer far outside the canvas is
  cropped to the new canvas: Photoshop does the same, but the history step is
  then not undoable *content-wise* for such layers unless the caller keeps the
  tile handles. Undo is snapshot-based (`fx-core::history`), so nothing is lost
  inside a session; saving after an Image Size does not keep the off-canvas
  pixels. Worth a note in ARCHITECTURE §4.3 when D-015 is revisited.
- **`grid` levels for a grown canvas.** `RotateCanvas` swaps the document size
  and every image keeps its own level count; a later mip read recomputes it, but
  a *dirty* derived tile of the old shape is left as it was (the images are
  re-created, so their grids are new — verified by the tests, but a large
  document pays for regenerating all mips after a turn). If S17 is tight,
  regenerating only the levels the viewport reads is the next lever.
- **Crop (T03) should reuse `permute_canvas`'s validation-first shape**: the
  "compute every new image, then commit" layout is what makes an interrupted
  rotation leave the document untouched; crop + straighten need the same
  property.
