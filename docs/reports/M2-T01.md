## What was done

### `crates/fx-core/src/command.rs` — every `M2` command

All commands validate fully before the first write, so a failed command
leaves the document untouched (tested for each error case), and each returns a
`CommandEffect` that lists exactly what changed.

* **`SelectLayers`** — resolves and dedupes every ref, then replaces
  `Document::selected`; `selection_only`, so `History` records no step.
* **`AddLayer`** — directly above the active layer, inside the group the
  active layer lives in (or on top when nothing is selected); the new layer
  becomes the only selected one. Default names come from the per-kind
  counters: `Layer 1`, `Group 1`, `Color Fill 1`, `Curves 1`, `Levels 1`,
  `Brightness/Contrast 1`, `Exposure 1`, `Hue/Saturation 1`, `Invert 1`. A
  pixel layer is created empty (`TiledImage::new`, no tile memory
  regardless of document size). History labels: `New Layer`, `New Group`,
  `New Fill Layer`, `New Curves Adjustment Layer`, …
* **`DeleteLayers`** — a deleted group takes its children; selection moves to
  the first remaining row *below* the lowest deleted row, else to the nearest
  remaining row above the topmost deleted one. Deleting everything is allowed
  and leaves no selection.
* **`DuplicateLayers`** — copies sit directly above their originals and get
  the `" copy"` suffix; a duplicated group gets fresh ids for its whole
  subtree, but only the duplicated layer is renamed (Photoshop). Tile handles
  are shared — no pixel copy (`duplicate_layers_share_tile_handles`).
* **`MoveLayer`** — rejects a parent that is not a group, an index past the
  end, and moving a layer into itself or one of its descendants. `index` is a
  position in the target list *after* the layer is taken out of it (documented
  on the variant), which is what a drag means.
* **`GroupLayers`** — wraps the selection in a new group placed at the
  topmost selected layer's position, keeping relative order bottom → top,
  pulling layers out of other groups if need be; grouping inside a group makes
  a subgroup. The new group is selected. `Group 1`/`Group 2` come from the
  group counter.
* **`SetLayerProps`** — the reference implementation plus M2 validation: an
  empty patch, an empty name, `PassThrough` on a non-group, and a clipping
  mask on a layer with nothing below it are all rejected. Range checks on
  `opacity`/`fill` were already there. A failing command applies nothing (the
  test sets a valid `name` next to an out-of-range `opacity` and asserts the
  name did not land).
* **`OffsetLayer`** — pixel layers only (`NotAllowed` otherwise), rejects
  `locked_position` with `CommandError::Locked`, and both axes are computed
  before either is written (overflow → `InvalidValue { field: "offset" }`).
  Pixels are never touched: the tile handle is identical afterwards. A linked
  mask follows automatically — the renderer places a linked mask at the
  layer's offset and an unlinked one at the document origin
  (`fx-render::program::ProgramBuilder::mask`), so there is no separate mask
  offset to change.
* **`AddMask`** — `RevealAll` sets every level-0 slot to `Solid(max)`,
  `HideAll` leaves the image all-`Empty` (mask value 0); neither uses tile
  memory, and the mips stay dirty for the M1-T05 scheduler. Masks are
  document-sized, enabled, linked, `outside_value` matching the fill.
  Rejected: a group, a layer that already has a mask, and `RevealSelection`
  (needs selections, M5) with a clear error instead of a `todo!()`.
* **`DeleteMask`** — `apply: false` just removes the mask. `apply: true`
  multiplies the layer's alpha by the mask (straight alpha, D-005: colour is
  untouched), tile by tile on the rayon pool, and commits one slot per tile.
  Driven by the mask's tiles: a `Solid(max)` mask tile changes nothing, an
  `Empty` (mask 0) tile needs no pixel read, and a layer tile with no pixels
  is skipped, so a reveal-all mask costs nothing at all. A pixel that ends up
  fully transparent is cleared to zero, which lets a fully hidden tile
  collapse back to `Empty` instead of costing memory. The new image is built
  aside and swapped in once, so a store error part-way changes nothing; the
  mask is put back on every error path. Non-pixel layers, missing masks, and
  an unlinked mask on a layer that has a non-zero offset (its grid sits at the
  document origin, so the tile pairing would be wrong — see Deviations):
  `NotAllowed`, document untouched.
* **`SetAdjustment`** — only adjustment layers, and only parameters of the
  same kind (a `Curves` layer cannot become a `Levels` layer).

Helpers added: `resolve_all` (resolve, dedupe, optionally drop descendants of
another resolved layer), `children_ref`/`children_mut`/`id_at_path`,
`insert_above_active`, `deep_copy`, `collect_subtree`, `remove_layer`,
`selection_after_delete`, `mask_image`, `bake_mask`/`bake_tile` +
`apply_mask_alpha`/`scale_alpha8`/`scale_alpha16`, `validate_name`,
`checked_offset`. `CommandError` gained one variant, `Tile(#[from] TileError)`
(see Deviations).

### `crates/fx-core/src/document.rs` — names and panel order

* `name_counters: [u32; NameKind::COUNT]`, private, plus
  `pub(crate) enum NameKind` (`Pixel`, `SolidFill`, `Group` and one per
  adjustment kind) with `stem()`/`of_adjustment()`, and
  `next_default_name(kind) -> String`. Counters are cloned with the document,
  so undo restores them and a second document starts at `Layer 1`.
* `pub fn panel_order(&self) -> Vec<LayerId>` — the ids in the order the
  Layers panel draws them (top → bottom, children under their group). The
  delete-selection rule, duplicate order and group placement need rows, not
  just the tree.

### `crates/fx-engine/src/layers.rs` — `Document` → `Vec<LayerInfo>`

New file with `pub fn layer_infos(doc: &Document) -> Vec<LayerInfo>`:
panel order, `depth` per group level, `LayerKind` → `LayerInfoKind` 1:1,
`has_mask` = a mask exists, `expanded` only for groups, `locked` = either
lock flag, `selected` from `Document::selected`. It reads structure and flags
only — no tile is touched, so it is `O(layers)`, safe to call for every
`layers` message on a 30 000² document. `lib.rs` gained exactly one line,
`pub mod layers;`.

## Measurements (performance tasks)

None: M2-T01 is not a performance card. For the record, the mask bake is the
only part that touches pixels: work is driven by the mask's tiles
(`cols × rows` per row band, `BAKE_COLUMNS = 16` tiles in flight, one 256²
Rgba16 tile = 512 KB), the per-tile work runs on `rayon`, and nothing holds a
buffer proportional to the document — the new image is the same slot grid the
layer already has, with the new tiles living in the store where its budget
governs them.

## Deviations from the task card

1. **`AddLayer` against a *selected group*.** The card says "above the active
   layer, inside its group if the active layer is in a group". I implemented
   it as "a sibling directly above the active layer, in whatever list that
   layer lives in": with a child selected, the new layer lands inside that
   group; with a root-level group selected, it lands above the group. If Rob
   wants Photoshop's "a group row selected means insert *inside* at the top",
   that is one branch in `insert_above_active` plus one test. Asserted in
   `add_layer_above_a_selected_group_stays_at_its_level` and
   `add_layer_goes_inside_the_group_the_active_layer_lives_in`.
2. **"DeleteMask{apply} over the mask's non-uniform tiles only."** Taken
   literally, skipping *every* uniform mask tile would be wrong: a `Solid`
   mask tile of 50 % still has to halve the alpha under it. What is skipped
   (no store read, no pixel pass) is what cannot change a pixel — a
   reveal-all `Solid(max)` mask tile, and any tile where the layer has no
   pixels. Uniform *partial* tiles are scaled, a whole-tile uniform layer tile
   is materialised without a store read, and stored mask tiles are the normal
   per-pixel pass.
3. **Fully hidden pixels are cleared.** When the multiplication drives a
   pixel's alpha to 0, its RGB is zeroed as well: the colour cannot show, and
   it lets a completely hidden tile collapse back to `TileSlot::Empty`
   instead of holding transparent-but-nonzero RGB (tested in
   `delete_mask_apply_of_a_hiding_mask_empties_the_tiles`).
4. **A disabled mask is still applied by `DeleteMask { apply: true }`.** The
   `enabled` flag governs live compositing; "apply" bakes what the mask
   stores. Documented in the code.
5. **`DeleteMask { apply: true }` refuses an unlinked mask under an offset
   layer.** The bake pairs layer tile *(tx, ty)* with mask tile *(tx, ty)*,
   which is the renderer's alignment only while both grids share an origin:
   `fx-render::program` draws a *linked* mask at the layer's offset and an
   *unlinked* one at the document origin, so with an unlinked mask and a
   non-zero offset the pairs are wrong. The command returns `NotAllowed` and
   changes nothing (asserted, pixel content and mask included); a linked mask
   under the same offset bakes normally, as does an unlinked mask on an
   unshifted layer. Baking a mask whose grid really is shifted means moving
   one of the two grids — see Suggestions.
6. **`DuplicateLayers` renames only the duplicated layer.** A duplicated
   group's children keep their names (Photoshop's behaviour); the card only
   says `" copy"` suffix.
7. **`SetAdjustment` requires the same adjustment kind.** An adjustment
   layer's type is part of its identity (Photoshop's Curves dialog never
   turns a layer into a Levels layer); a mismatch is
   `InvalidValue { field: "adjustment" }`.
8. **`SetLayerProps`' "M2 validation" is my reading of it** (the card does not
   enumerate): empty patch, empty name, `PassThrough` outside a group,
   clipping with nothing below. Two judgement calls there: `clipped: false` on
   the bottom layer is allowed, and a group *may* be clipped (the program
   builder has clipping groups).
9. **`MoveLayer.index` semantics** are documented on the variant: a position
   in the target list after the moved layer has been taken out, `index == len`
   = top, so moving a layer one slot up or down is the same command at any
   current position.
10. **Duplicate refs and nested selections** in `DeleteLayers`,
   `DuplicateLayers` and `GroupLayers` are deduped, and a layer nested inside
   another selected layer is dropped (its ancestor covers it). `SelectLayers`
   keeps every selection, nesting included.
11. **`CommandError` gained `Tile(#[from] TileError)` and lost `PartialEq`.**
    `DeleteMask { apply: true }` reads stored pixels through
    `TileStore::get`, which can fail (scratch I/O, corrupt tile), and rule 9
    forbids hiding that. `TileError` wraps `std::io::Error`, so it cannot be
    `PartialEq` and neither can a type holding it; `fx-io`'s `IoError` wraps
    `TileError` the same way (`#[error(transparent)]`). Nothing compared
    `CommandError` values (`grep`ed the workspace); the new tests use
    `matches!`.
12. **`Document` gained a private field** (`name_counters`); `Document::new`
    and every public API are unchanged, and all construction already went
    through `new`. `Document::panel_order` is a new public method (documented).

## Open problems / suggestions

- **Wire the two halves together (M1-T08 / M2-T06).** `layer_infos` is not
  called anywhere yet: the engine thread still has to build `EngineToUi::Layers
  { doc, revision, layers }` (on `structure_changed`, `props_changed`, or a
  selection change) and the Layers panel has to draw it.
- **`DeleteMask { apply: true }` ignores `locked_pixels`.** A pixel-locked
  layer arguably should refuse a destructive pixel edit (Photoshop does); the
  card only ties `Locked` to `OffsetLayer`, so I left it out rather than
  inventing a rule. Same question for painting over a pixel-locked layer in
  M4.
- **Bake an unlinked mask under an offset layer.** The current command
  refuses it because the mask's tile grid sits at the document origin while
  the layer's is shifted; doing it properly means reading the mask through the
  same up-to-4-tile quad the renderer uses (`program::Quad`), which is a
  bigger change than the card asked for. Worth a follow-up if the Layers
  panel lets a user unlink a mask.
- **Adjustment parameter ranges are not validated** — a `Levels` gamma of 0
  or unsorted `Curves` points go through to the LUT baker. If the dialogs can
  produce them, the LUT code (Claude's) should reject them or the command
  should; worth a follow-up card.
- **`GroupLayers` reworks the stack between the selected layers** (the group
  forms at the topmost position and the selected layers move together), so an
  unselected layer that sat between two selected ones ends up below the group.
  That matches Photoshop's "Layer ▸ Group Layers" but is worth a manual check
  on a deep selection.
- **The mask bake reads tiles on the engine thread.** Only the *render* thread
  must never block (`AGENTS.md` §3), and `TileStore::get` on cold tiles is a
  positioned read (≈0.5–1 ms each), so a mask bake over a spilled 30 000²
  layer could stall the engine for a while. If it shows up in M2-T08, the bake
  should become a job on the worker pool with the commit applied from the
  engine thread.
- **`layers.rs` and `Document::panel_order` now walk the tree the same way
  twice.** I left `layers.rs` as it is (it was frozen for this branch); a
  later cleanup could build `LayerInfo`s on top of `panel_order`.
