# M0-T02 — `xtask`: bundle and run

Agent: Buffy (Freebuff)  ·  Branch: `task/M0-T02-xtask`  ·  Status: ready for review

## Plan (written before coding)

1. New binary crate `tools/xtask`, added to `[workspace] members` but **not**
   to `default-members`, so a plain `cargo test`/`cargo check` never builds it.
   Dependencies limited to approved workspace crates: `clap`, `anyhow`,
   `tracing`, `tracing-subscriber` — deliberately **not** `cef-dll-sys`, so
   compiling xtask needs no CMake and no CEF download.
2. `main.rs`: clap CLI with `bundle [--release]` and `run [--release] [-- args]`.
3. `common.rs` (portable): workspace root from `CARGO_MANIFEST_DIR`, target dir
   from `CARGO_TARGET_DIR` else `<workspace>/target`, profile → directory name,
   `cargo build -p fx-app` helper, and the CEF runtime locator.
4. `win.rs`: the bundle itself — mirror the CEF runtime into
   `target/<profile>/Fotox/`, apply Graphite's `remove_unnecessary_cef_files`
   list as a copy filter, then copy `fotox.exe` in.
5. Step 4 of the card ("re-copy only files whose size/mtime changed") means the
   copy must be incremental, unlike the reference's `clean_dir` + full copy.
   Compare size and mtime, copy only on difference, and carry the source mtime
   onto the copy so the *next* run can compare instead of copying.
6. Because the copy is incremental rather than from a clean directory, also
   prune entries in the bundle that are no longer produced, otherwise a CEF
   version bump (or a widening of the removal list) would leave stale DLLs.
7. `.cargo/config.toml`: `[alias] xtask = "run -p xtask --"`.
8. Verify against the acceptance: `cargo xtask run` must start the placeholder
   `fotox.exe` from the bundle folder, print its M0 message and exit. Then the
   AGENTS.md §4 checks, and a second `bundle` run to prove the incremental path
   actually skips unchanged files.

## What was done

**The crate.** `tools/xtask` (binary `xtask`) with `bundle` and `run`
subcommands. It is a workspace member but not a default member, so the engine
test/check loop is untouched. It depends on `clap`, `anyhow`, `tracing` and
`tracing-subscriber` only.

Two deliberate structural choices, both explained under *Deviations*:

* **No `build.rs`, no dependency on `cef-dll-sys`.** The reference bundle crate
  pulls its CEF path out of `DEP_CEF_DLL_WRAPPER_CEF_DIR`, which requires
  compiling `cef-dll-sys` — and therefore CMake and the CEF download — just to
  build the helper. The card instead names the layout explicitly
  (`$CEF_PATH/<version>/<os_arch>/`), so `common::cef_runtime_path` reads
  `CEF_PATH` (set by `.cargo/config.toml`, with a `third_party/cef` fallback)
  and walks one directory level at a time. `cargo xtask` therefore compiles and
  reports its errors on a machine with no CEF at all.
* **The removal list is a copy filter, not a post-copy delete.** The reference
  copied everything, then deleted what it did not want. Filtering during the
  walk yields the same bundle without ever writing the excluded bytes.

**Incremental copying and pruning.** `copy_file_if_changed` skips a file when
size and mtime both match the source, and after a copy it stamps the source's
mtime onto the copy so the next run can compare rather than copy. Windows
already preserves the timestamp through `fs::copy`; doing it explicitly makes
the skip check depend on our own behaviour instead of the platform's. A
timestamp that cannot be set is counted and warned about, never fatal — the only
consequence is a redundant copy next time.

Because the bundle directory is no longer wiped, one addition was necessary:
`prune_stale` deletes bundle entries CEF no longer provides (or that the filter
excludes) and then the directories left empty. Without it, upgrading CEF would
leave the previous version's `libcef.dll` sitting in the bundle — a confusing
failure mode that costs far more time than the pruning costs. `fotox.exe` is on
an explicit `BUNDLER_OWNED` list so the prune pass cannot delete the app it just
placed there.

**Paths are resolved, not guessed.** The workspace root comes from
`CARGO_MANIFEST_DIR`, `CARGO_TARGET_DIR` is honoured, and the resolved target
directory is passed to the nested `cargo build`, so the directory the bundle is
written to is provably the one the build wrote to. `cargo xtask bundle` works
from any subdirectory of the repo (verified from `target/`).

**Failure modes are explicit** (AGENTS.md §3.9 — no silent fallbacks): a
missing CEF root, no version directory, several version directories, and "cargo
build produced no executable" each produce a specific message rather than a
guess or a panic.

The launch line logs the pass-through arguments, which is what makes
`cargo xtask run -- <args>` verifiable before M0-T03 gives `fotox.exe` real
flags.

| `cargo xtask run`, everything up to date | — | 0.68s to app start | — |

**Honest reading of the incremental copy.** It saves about 0.2s per iteration
here, because the machine writes 347 MB in ~0.26s. The dominant cost of
`cargo xtask run` is `cargo build -p fx-app`, not the copy — so step 4's benefit
is real but small on this NVMe, and it should not be described as the reason
iterations are fast. The larger effects are the 927 files that are never written
(and so never need stat/open/close on later passes) and the pruning, which is a
correctness property rather than a speed one.

## Deviations from the task card

1. **The CEF runtime path comes from the `CEF_PATH` environment variable, not
   from a `build.rs` reading `DEP_CEF_DLL_WRAPPER_CEF_DIR`** as the reference
   does. The card states the layout to use (`$CEF_PATH/<version>/<os_arch>/`),
   and this keeps `cef-dll-sys` — and therefore CMake and the CEF download —
   out of xtask's dependency graph. Effect on behaviour: none for a correctly
   downloaded CEF; a machine with several downloaded CEF versions gets an
   explicit error instead of an arbitrary pick.
2. **The removal list is applied as a copy filter rather than by deleting after
   the copy.** Same resulting bundle, less I/O. The list itself is transcribed
   unchanged from `reference/graphite-desktop/bundle/src/win.rs`.
3. **A prune pass was added**, which the card does not mention. It is required
   by making the copy incremental (step 4) rather than copying into a wiped
   directory as the reference does; see *What was done*.
4. **`copy_file_if_changed` also aligns the copy's mtime with the source.**
   Needed to make the size/mtime comparison of step 4 actually converge rather
   than re-copying forever on a platform that does not preserve mtime.
5. The launch log line includes the pass-through arguments. Not requested; it is
   what makes `run -- <args>` verifiable, since the M0 placeholder ignores argv.
6. `-p xtask` is not added to the AGENTS.md §4 `cargo fmt` package list. That
   line predates this crate, and editing `AGENTS.md` is not in this card — see
   the suggestion below. Formatting was checked explicitly instead.

## Open problems / suggestions

1. **Release bundles do not yet embed the UI.** `.cargo/config.toml` points
   `GRAPHITE_RESOURCES` at `./ui`, so a `--release` bundle still reads the UI
   from a path relative to the repo and will not run on its own. The
   `embedded_resources` feature on `fx-app` is exactly for this, and
   `Cargo.toml` already documents it, but this card does not mention features
   and the reference passes none either. Worth deciding in M0-T03 whether
   `cargo xtask bundle --release` should pass `--features embedded_resources`,
   because M0-T07's "works from a clean clone" checklist will otherwise pass on
   the dev profile only.
2. **`cargo fmt` in AGENTS.md §4 does not cover `tools/xtask`.** The list is a
   fixed set of `-p` flags, so a new crate silently escapes the format gate.
   Either add `-p xtask` there or switch that line to `--all`, so this cannot
   happen again for the next tool crate.
3. **The "CEF is not downloaded" error is unreachable through `bundle`.**
   `bundle` runs `cargo build -p fx-app` first, and `cef-dll-sys` downloads CEF
   into `$CEF_PATH` as part of that build, so by the time the locator runs the
   directory always exists. It stays as a guard for a future
   bundle-without-building path; I could not exercise it, and I am flagging it
   rather than claiming it as verified. (It was *almost* exercised: pointing
   `CEF_PATH` at a nonexistent directory did not error, because the build
   created that directory and downloaded 592 MB into it. I removed the
   directory afterwards.)
4. **`bundle` is the only way to launch, and it always rebuilds first.** There
   is no "just run what is in the bundle" command. Once M0-T03 lands and the app
   takes real flags, restarting only the UI is the common loop (the UI is read
   from `./ui` at runtime), and paying for `cargo build` on every launch will
   become the most annoying part of the workflow. A `cargo xtask run --no-build`
   would be cheap to add.
5. `--release` currently builds the whole app in 2m 00s with `lto = "thin"` and
   `codegen-units = 16`. Worth a look in M0-T07, but not a problem now.
