## What was done

* **`debug:load-b3`** (menu *Other ▸ Benchmarks ▸ Load B3 onto This Document*): builds B3 on top of the active document — open B1 first, it becomes the background — as a job on a worker thread with a progress message: 199 sparse pixel layers + 20 adjustment layers (Curves, Levels, Hue/Saturation, Brightness/Contrast, Exposure, mild settings), 220 layers in total with the background. Deterministic (seed 3). Built outside the history (a benchmark setup, not an edit): the history restarts from it.
* Each pixel layer: a rectangle covering 2–10 % of the area (random aspect, position, colour), a random blend mode (every mode except Pass Through), opacity 35–100 %, with a soft 64 px edge. **Deviation:** the layers are one colour with a feathered edge, not photographic content — interior tiles are `Solid`, only edge tiles hold pixels. 199 photographic layers of that size would be ~86 GB; this keeps B3 at a few GB of (compressible) tiles while the compositor still blends every layer on every tile it covers. If B3 should also stress the atlas upload path harder, the interior could get `gen`'s content at the cost of scratch space.
* The frame-time overlay also moved into that submenu.
* `fx-engine/src/b3.rs`, 2 tests (219 new layers = 199 pixel + 20 adjustment, same seed → same document; interior tiles are solid).
* Layers panel fix found on the way: rows printed "null" before the name (the DOM's `append` stringifies `null`; `el.js`'s `add` skips it).
