## A. Canvas boundary and rendering — Critical

### R2-01  The active area does not match the canvas size
There is a clear mismatch between the defined project/canvas size and the effective editable area:
the rectangle the user can paint in and the rectangle that clips the composite are not the same.
- Verified: the visible *tile range* is clipped to the document — `fx-render/src/viewport.rs:149`
  `visible_doc_rect` intersects the rotated viewport quad with `0..doc_w, 0..doc_h`, and
  `visible_tiles` (line 170) derives the range from it. So the canvas is not ignored everywhere.
- Lead: the unclipped part is the draw itself — see R2-02. Also compare the *input* clip (where a
  brush may paint) with the composite clip, in `fx-engine/src/view.rs` / the tool context's
  document rect, against `plan.doc_rect` in `fx-render/src/frame.rs`.
- Repro needed: a document at a preset size, zoom 100 %, paint to each edge; note where a stroke is
  accepted but not shown, or shown but not accepted.

### R2-02  Canvas bleed when zooming out
Zooming out leaves image areas that should be clipped outside the canvas boundaries visible.
- Verified: `fx-render/src/frame.rs:60-70` computes each composite tile's screen rectangle from the
  tile grid alone (`tile_screen_rect`, line 174) and the viewport shader (`gpu/viewport.wgsl:81-85`)
  draws that quad with no clip of its own. `FramePlan.doc_rect` exists but is used only for
  instance 0 — the transparency-checkerboard quad (viewport.wgsl:73-79). `build_program(doc, level,
  tx, ty)` (`fx-render/src/program.rs:247`) has no document size either, so a layer whose image is
  bigger than the canvas (a paste, a move, a placed file) contributes ops for pixels outside the
  document, and those land in the edge composite tiles.
- Consequence: the part of an edge tile that lies outside `doc_rect` is painted, so layer content
  outside the canvas shows. It is most obvious when zoomed out, where the whole document and its
  edge tiles are on screen at once.
- Candidate fix (pure logic, testable without a GPU): clamp every `TileDraw.dst` to
  `plan.doc_rect` and remap `src` to match, in `plan_frame`. The existing tests in `frame.rs` cover
  the planner, and `gpu/viewport_tests.rs` covers the quad building.

### R2-03  Visual artifacts while moving a layer
Moving a layer cuts the image off temporarily; the full image comes back only after the move ends
or restarts.
- Lead: the transform preview path (`fx-engine/src/transform_preview.rs`) and the layer's offset in
  the compositor — the live preview probably draws at a different level, or draws the layer from
  tiles whose mip has not caught up with the offset until the move commits.
- Related and already fixed once: `crates/fx-engine/tests/paste_zoom_flow.rs` — a pasted layer whose
  pyramid was shorter than the canvas's read the wrong tiles.

## B. Transform tool and state

### R2-04  A transformation preview is cancelled by any outside action
**Partially fixed — `R2-04: preserve transform while editing another layer's properties`.** The
cause of the visibility example is explicit in `fx-engine/src/engine.rs::command`: it ended the
transform for every non-Transform command. A `SetLayerProps` command targeting another layer now
keeps the box and preview. The engine regression test
`showing_another_layer_keeps_the_transform_box_and_its_pending_change` hides a Background layer,
moves a duplicate in Free Transform, shows Background, then commits the transform; it passes.
Other outside commands still cancel the box and need separate decisions about whether to preserve
or commit it, especially commands that change the transformed pixels or document geometry.

Doing anything else while a transform control preview is on screen — e.g. toggling the visibility
of a hidden layer — instantly cancels the transformation and reverts the image to its default
proportions.
- Lead: `fx-engine/src/transform_preview.rs`, plus the "any other command" paths in
  `fx-engine/src/engine.rs` that end or drop a preview; the S2-01 fix now calls `end_stroke()` when
  a `tool:` action arrives, which may also be ending the transform preview.

- Verified entry point: `fx-engine/src/tools/lasso.rs` (the tool already keeps an open path, and

- Tool-options plumbing is already in place for a new option-bar entry (`ui/js/data/options.js`,

### R2-08  The colour picker lags and picks the wrong colour

## E. UI and layers panel — feature requests

### R2-12  The blending-mode drop-down cannot be scrolled
**Fixed — `R2-12: keep a popup open while its own list scrolls`.** The capture-phase document
`scroll` handler in `ui/js/popup.js` closed the blend-mode popup on the first wheel scroll of its
`.optlist`. It now ignores scroll events inside an open popup, while scrolls elsewhere still close
it. In the browser UI with a 28-row list in a 560 × 400 window, the list remained open and its
`scrollTop` reached about 136; the last rows, including Luminosity, became visible. Native app
confirmation remains open.

Once the layers panel's blending-mode list (Normal, Vivid Light, …) is open it does not scroll, so
the entries at the bottom cannot be reached.
- Verified: the list *has* the CSS to scroll — `.optlist` is `max-height: 340px; overflow-y: auto`
  (`ui/css/menus.css:57-62`) and `openDropdown` (`ui/js/popup.js:136`) fills it. The blend list is
  ~30 rows, so it is capped and scrollable in principle.
- Suspicion: the placement, not the list. `place()` (`ui/js/popup.js:26-68`) measures the popup and,
  when a `below` popup would overflow the bottom of the window, flips it to `anchorRect.top - hgt`,
  then clamps to `pad = 6`. The blend button sits in the panel head, so the flipped popup can be
  clamped to the top of the window with its lower part off screen.
- Next step: reproduce in the browser UI (`cd ui && python tools/serve.py`) and measure the popup's
  rect against the window; then decide whether the list needs `max-height` from the *available*
  space, a scrollbar that is visible, or a proper flip.

## F. Performance

### R2-17  A 20 000 × 20 000 document is extremely slow
- What the 2026-09-26 review already found and what has been fixed since: whole-image tile vectors
  in filters/merges (S1-03, now batched by 16 tiles), composite/mip preparation on the engine thread
  (S3-01, now on the AI worker), concurrent saves, and worker panics.
- The 20k² case is 400 M pixels: level 0 is 79 × 79 = 6 241 tiles, and one 256² RGBA16 tile is
  512 KiB, so a fully populated level 0 is 3.2 GiB; `level_count_for(20_000, 20_000)` is 8
  (`fx-tiles/src/image.rs:108`), so the pyramid is another ~1.1 GiB on top.
- Measure before changing anything: a 20k² document's time to first frame, a zoom in/out, a brush
  stroke, a filter, save, and undo. The flight recorder already logs timings
  (`fx_engine::trace`, `trace:download`).
- Suspicion to test first: history snapshots (whole-document state per step) and the mip pyramid's
  cold build after open.
