# M1-T09 — PNG and JPEG import

Agent: Claude  ·  Branch: `task/M1-T09-png-jpeg`  ·  Status: done

## What was done

* The band assembly moved from `tiff.rs` to a shared `band.rs` (unchanged code), used by all three importers.
* **PNG** (`png.rs`, `png` crate): 8/16-bit; gray, gray+alpha, RGB, RGBA, palette with or without tRNS (via `EXPAND | ALPHA`, so every variant arrives as gray+alpha or RGBA). Non-interlaced rows stream straight into the band. Interlaced PNGs are decoded whole, capped at 16 384 px per side (larger → `Unsupported` with the size). ICC (iCCP) → `ColorProfile::Icc`; pHYs in metres → ppi; default 72. A PNG that ends early is a decode error.
* **JPEG** (`jpeg.rs`, `zune-jpeg`): baseline and progressive 8-bit, decoded straight to RGBA; ICC from APP2; EXIF orientation 1–8 applied (own ~30-line parser for tag 0x0112, both byte orders); JFIF density (dpi / dpcm) → ppi. zune's default 16 384 px size limit is raised to JPEG's own 65 535.
* Tests (`png_jpeg_tests.rs`, 9 new; fx-io total 18): PNG RGBA8 with 300 ppi, RGB16 (big-endian samples), gray+alpha 16, gray 8, palette with tRNS, truncated file; JPEG upright, orientation 6 and 3 (EXIF segment spliced into a committed 681-byte fixture made with Windows' JPEG encoder: `tests/data/red-blue-64x32.jpg`), EXIF parser and the orientation mapping for all 8 values.

## Deviations from the task card

1. **JPEG is not streamed.** `zune-jpeg` decodes a whole image at once, and applying an EXIF rotation needs every row anyway; the decoded RGBA8 image is then cut into bands like the other formats. Peak memory for a JPEG import is `width × height × 4` bytes (3.6 GB for a 30 000² JPEG). A streaming JPEG path would need a scanline decoder (e.g. `jpeg-decoder` with a row callback, not in the approved crates) and could not apply rotations 5–8 without a second pass; worth a decision if huge JPEGs matter.
2. No interlaced PNG test: the `png` encoder cannot write Adam7. The code path is the plain `next_frame` call.
