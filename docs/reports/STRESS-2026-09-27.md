# Stress tests at scale — 2026-09-27

`crates/fx-engine/tests/scale.rs` drives a real engine (engine + render
threads on the GPU, the same messages the UI sends) with thousands of layers,
deep groups, huge canvases and many documents, and prints what every step
took and the memory at checkpoints. All `#[ignore]`d:

```
cargo test --release -p fx-engine --test scale -- --ignored --nocapture --test-threads 1
```

Knobs: `FOTOX_STRESS_LAYERS`, `FOTOX_STRESS_DEPTHS`, `FOTOX_STRESS_SIZE`,
`FOTOX_STRESS_DOCS`, `FOTOX_STRESS_DIR` (scratch and saved files — **use
D:**, C: is nearly full), `FOTOX_STRESS_CSV=1` (append to
`bench/results.csv`). "View settled" = the last frame of the burst an action
started (no frame for 750 ms after it).

Machine: Rob's PC (16 GB RAM, ~4–8 GB free during the runs, RTX 3060, 12
threads), release build. Not the idle reference machine: other apps were
open, so memory numbers are pessimistic.

## Fixed in this round

| # | What | Symptom | Fix | Gate |
| --- | --- | --- | --- | --- |
| F1 | Thumbnails queued with `rayon::spawn`, one per layer | **The process aborted** (`thread '<unknown>' has overflowed its stack`) at the first Undo of a 2000-layer document with the Layers panel's thumbnails wanted. A thumbnail computing mips waits on a `par_iter`; a waiting rayon worker runs other queued jobs on the same stack, which wait in turn — the stack grew with the queue. | `thumbs::ThumbQueue`: two threads of its own, outside the pool (a non-worker thread waiting on `par_iter` just blocks), one waiting job per (doc, layer) — a newer request replaces a waiting one, so 20 undos no longer queue 20 × N renders. | `stress.rs`: `thousands_of_queued_thumbnails_do_not_overflow_a_worker_stack` (aborted before, in 1 s), `a_waiting_thumbnail_job_is_replaced_not_repeated` |
| F2 | Render thread kept the last document | Closing the last open document kept all its tiles in memory (20000² 16-bit: 4.6 GiB hot after closing) until another document was drawn: `TilePipeline` held its `snapshot` and the tile programs holding its tile handles. | `TilePipeline::forget_document` when a frame has no document. After closing: 0 MiB hot, 130 MiB working set. | `scale.rs` `huge_canvas` asserts the tiles are freed on close |

## Open — for Rob to decide

**O1 — groups nested ≥ 60 deep save but never reopen.** The `.fxd`
manifest is JSON; serde_json refuses more than 128 levels ("recursion limit
exceeded"), and each group level costs two. 50 deep reopens, 60 does not.
Nothing stops the user from nesting that deep (each Group Layers is ~1.6 ms),
so a file can be saved that Fotox cannot open. Photoshop caps nesting at 10
levels. Options: (a) cap nesting in the engine (Group, Move into group, PSD
import) at a documented depth and refuse deeper; (b) read with the limit
disabled (`serde_json` `unbounded_depth` + `serde_stacker`) — then find the
depth where the recursive render/save walks overflow instead. Recommended:
both — a cap (e.g. 50) plus a reader that never refuses what the writer wrote.

**O2 — every edit resends the whole layer list.** `after_edit` sends
`Layers` with every layer on every command; the UI `JSON.parse`s it and
rebuilds the panel. Measured per command (`per_edit_costs_by_layer_count`):

| layers | build list | encode | decode (≈ UI parse) | message |
| --- | --- | --- | --- | --- |
| 1 000 | 0.2 ms | 0.3 ms | 1.7 ms | 281 KiB |
| 2 000 | 0.8 ms | 0.9 ms | 4.7 ms | 562 KiB |
| 5 000 | 4–7 ms | 3–5 ms | 21–27 ms | 1.4 MiB |

So adding the 2000th layer costs ~4× the 200th (add + select + fill +
deselect: 16 ms → 67 ms), and building 2000 layers takes 106 s instead of
~30 s; at 5000 layers every click costs ~40 ms of list traffic before the
panel even redraws. Fix: send a diff (changed layers + order) or only the
changed layers' infos for property edits; full list only on structural
changes.

**O3 — memory budgets ignore the machine.** Hot 5 GiB + warm 3 GiB are
fixed (`TileStoreConfig::reference_machine`), and the GPU atlas (6 GiB) +
composite cache (0.5 GiB) are allocated up front: the process's private bytes
jump from 274 MiB to ~7 GiB as soon as the first document is drawn, whatever
its size. On this PC (other apps open) that pushes Windows into the page file
— on C:, which lost ~9 GB of free space in 20 s during the 30000² run
(stopped). Saving is probably where it shows: a save's time is almost all
zstd, and zstd's time per tile grew with the memory in use (0.3 ms at 850
tiles, 7 ms at 41 000 tiles = 10 GB held) — consistent with paging, not
proven. Fix: size the hot/warm budgets from free physical memory at start
(and shrink under pressure), size the atlas from the adapter's VRAM and grow
it lazily.

**O4 — 100 % zoom on 2000 layers takes 3.5 s to fill in** (fit → 100 %:
~12 view tiles, each blending the ~100 layers that have pixels there; the
upload budget is 48 source tiles a frame). Fit is fine (11 ms). Worth a look
at the upload budget / program building when the stack is deep.

## Measurements

### `thousands_of_layers` — 4000 × 3000 8-bit, 2000 layers (after F1)

| Step | Result |
| --- | --- |
| add layer + select + fill + deselect, first / last 10 % median | 15.8 ms / 67.2 ms (O2) |
| build total | 106 s |
| tiles hot after the build | 4.76 GiB (rect edge tiles hold pixels; interiors are Solid) |
| thumbnails of all 2001 layers | 8.8 s |
| hide / show bottom layer, view settled | 255 ms / 45 ms |
| opacity drag (20 steps) | 20 ms a step, settled 450 ms after the last |
| zoom to 100 % / back to fit | 3.5 s / 11 ms (O4) |
| undo / redo median (thumbnails wanted) | 76 ms / 68 ms; 1203 thumbnails re-rendered by 40 steps |
| save as .fxd | 27 s for 1.4 MiB — 3.1 s for the same tiles in the engine-less benchmark. The time is zstd, whose cost per tile grew with the memory in use: most likely paging (O3), not proven |
| reopen: opened / view settled | 164 ms / 234 ms (lazy: 176 MiB working set) |
| merge visible / undo it | 12.3 s / 18 ms |

### `huge_canvas` — 20000 × 20000 16-bit (after F2)

| Step | Result |
| --- | --- |
| new document / first frame | 119 ms / 176 ms |
| full-canvas dithered gradient (3.2 GB of pixels) | 15.7 s, view settled at 16.1 s |
| 50 small layers on top | 232 ms median each |
| zoom to 100 %, pan (5 notches) | 179 ms, 8 ms median |
| hide / show the gradient layer | 30 ms / 28 ms |
| memory before saving | hot 4.6 GiB, warm 1.1 GiB, working set 6.5 GB |
| save as .fxd | 4.5 s, 331 MiB |
| after closing | 0 MiB tiles, 130 MiB working set (was 4.6 GiB: F2) |
| reopen / view settled / 100 % | 30 ms / 90 ms / 61 ms |

30000² was not run: it needs the page file on C: (O3).

### `many_documents` — 4 × 8000 × 6000 16-bit with a gradient layer

New document + gradient 1.8 s each; switching tabs 27 ms to a settled view;
4 open: 2.0 GiB hot; after closing 3: 515 MiB. Memory comes back.

### `deeply_nested_groups` — 2000 × 1500

Group Layers ~1.6 ms a level at any depth; save and reopen in milliseconds up
to 50 levels; 60 and deeper cannot be reopened (O1).

### Harness notes

* A visible selection redraws the view 8 times a second (marching ants), so
  the scenarios Deselect after each fill or the view never "settles".
* A run that aborts (stack overflow, OOM) skips its cleanup: delete
  `fx-scale-*` in `FOTOX_STRESS_DIR` by hand.
